**總分 = (3·C1 + 2·C2 + 1·C3) ÷ 18 × 10**，一位小數。權重來自這份文件原本就寫的排序依據：
C1「是否正在造成損害」為主、C2「依賴關係」次之、C3 只當 tiebreak。
**證據等級**（E1 實測／E2 推論／E3 判斷）標在各節內文，不進分數；硬門檻只收 E1。

**觸發點的寫法**：必須綁在**會自然發生的事件**上——下次動某個檔、某週的判讀、某指標跌破門檻、

#6 每一次單看都只值 0.6，但它已經被兩份 spec 記下又繞過——**重複本身是訊號**，

## CI gating（PR 自動跑測試）

**提出**: 2026-07-21
**狀態**: ✅ **L0＋L1 已完成**（PR #77 L0／#78 L1，2026-07-27）——`.github/workflows/tests.yml` 於 `pull_request` 跑 `pytest tests/unit`，`unit` 已是 ruleset 16977362 的 required check。**L2 刻意不做**（見階梯）。
**優先度**: **最高**——但使用者明示「不是現在」（07-27 已完成 L0/L1）
**依賴**: L2 需要「整合測試指向本機 Supabase」先完成（該前置已於 PR #79 完成，但 L2 仍刻意不納入）

**問題**：**這個 repo 完全沒有 CI。** 沒有任何 workflow 掛在 `pull_request` 上，
也沒有任何 workflow 跑 pytest。140 個測試（unit 127／integration 13）
**只在有人手動跑的時候才存在**。2026-07-21 的 PR #67～#70 全部零自動檢查就 merge。

**main 的現況**（用 rulesets API 查，**不是**舊的 branch protection 端點——那個會回 404 誤導）：

```
ruleset 16977362  main  enforcement=active
rules: deletion, non_fast_forward, pull_request
required_status_checks: []     ← 空的
```

保護已經在了（不能刪、不能 force push、必須走 PR），**只差 required check**。
所以這題不是「建立分支保護」，是「往既有 ruleset 加一個檢查」。

**為什麼優先度最高**：它是「把決策寫成機器會檢查的約束」這個機制的**前置**。
沒有 CI 的測試等於加了步驟的註解——寫一個「每日路徑零 AI」的測試，沒人跑的話，
下場跟那句說謊的 docstring 一樣。而且此專案的變更多由 AI 助理高速產出、
使用者 review 的常是散文摘要而非逐行 diff，**這種配置下自動閘門的價值比一般 solo project 更高**。

ROI 特別好：**測試已經寫好了，價值已建好只是沒被收割**，缺的只是一個 runner。

**階梯**：

| 階 | 內容 | 依賴 | 成本 | 狀態 |
|---|---|---|---|---|
| **L0** | `pull_request` 觸發 `pytest tests/unit`（127 個） | 無，隨時可做 | 約 1 分鐘/次 | ✅ PR #77 |
| L1 | 把 L0 加進 ruleset 16977362 的 `required_status_checks` | L0 | 設定變更 | ✅ PR #78 |
| L2 | 納入 `tests/integration` | ~~等 Supabase 隔離那條~~（已於 #2 完成） | — | ✗ 刻意不做（見 STATE） |

**L2 的陷阱，不可天真打開**：整合測試會寫正式 Supabase。直接開會分岔成兩條爛路——
不給憑證則測試 skip、拿到**假綠燈**（latent 失敗繼續躲著）；給憑證則**每個 PR 汙染正式資料庫**，
就是 2026-07-21 那件事乘以 N。

**一個必須一起想清楚的限制（使用者提出）**：
把決策寫成測試**並不能讓決策免於腐朽**。有人為了改核心邏輯順手調整測試時，
若測試沒記錄「什麼絕對不能動」，約束會無聲死掉——而且對方會真心認為自己在修一個過時的測試。

本 repo 已有現成反例：`test_filter_attaches_category_and_score` 在有憑證環境長期 fail，
處理方式是標成 latent 繞過，**一個已經爛在原地的測試**。

所以：測試贏過註解的地方**只有一個**，是讓違反的那一刻可見；它不會讓決策變永久，
沒有東西能做到那件事。決定會不會腐朽的不是媒介，是**那個東西有沒有記錄自己的重開條件**。
因此若要寫「決策型測試」，測試名稱與失敗訊息 MUST 帶上決策出處與重開條件，
讓對方必須**自覺推翻一個決策**而不是**修一個壞掉的測試**。
結構性補強只有 CODEOWNERS／path-scoped required review——不是防止刪除，
只是讓沉默的那條路變貴。

**問題**：每日與每週跑的不是同一條管線。

**為什麼會這樣（使用者親述的設計沿革，2026-07-21）**：專案早期是每天爬完就丟 LLM 產分析，

所以 `traffic_buffer.py` 的 "No AI calls" 與「每日不呼叫 analyze」**是刻意的成本決策，不是疏漏**。

但那條線畫的是**成本**，而充實被留在錯誤的一側：當年 `analyze()` 就是 LLM 那一步，

**實測成本（07-20 週一，E1）**：`GN 充實：35 篇中 35 還原連結、26 補摘要、26 補圖、9 失敗`，

|---|---|---|
| A | `traffic_buffer.py` 加一行 `cat.analyze(filtered)` | 一行。但把「每日零 AI」綁在「traffic 的 analyze 永遠不加 AI」上 |
| B | 每日 runner 直接呼叫 `enrich_articles` | 意圖明確，但 fail-soft 的 try/except 重複一份 |

- 90% vs 59% vs 74% 落差大而 n 僅 20/22/35。穩態速率未知——是幾個點，不是一條線。

### 選型結果（2026-09-05）

比較台：<https://claude.ai/code/artifact/c03d8035-ee5e-4257-b56d-12a1db0d6beb>
（五個候選列模型吃**同一批真實資料**渲染，唯一變因是列的形狀；列高與標題截斷率為載入後
以 `offsetHeight` / `scrollWidth` 實測，非設計稿標示值。）

**採用 E：響應式（B 形 × D 形）**——使用者 2026-09-05 選定，原話：
「B 跟 D 這兩種呈現方式，B 適合手機窄 width，D 適合電腦寬 width」。

- **窄（斷點以下）走 B 形**：左側 40px 方格（有圖放縮圖）＋ 兩行標題。
- **寬（斷點以上）走 D 形**：單行標題 ＋ 76×30 寬幅條靠右，**無圖的列自然結束、不需要佔位物**。
- 機制：同一個 DOM，用 `display:contents` 把內層 wrapper 溶掉讓元素在寬版變成同一列的
  flex item，再用 `order` 排序。**不需要重複的 DOM。** 比較台裡用 `@container`（樣本欄寬度由該頁
  控制，viewport 查詢會量錯對象）；**真實 app 的清單是滿版，那裡用 `@media` 等價**，且
  `shared.css` 本來就有 480px 斷點，窄寬兩形在本 codebase 不是新概念。
- **斷點暫定 560px，是推導不是實測**（E2）：D 的列首尾約吃掉 280px，標題要放得下約 20 個
  中文字需要 260px。比較台有寬度滑桿與即時截斷率，**實作前應該用它量一次再定案**。

**⚠️ E 的代價（明確認下，不要當成免費的折衷）**：兩套版面要一起維護，且**斷點從此是承重的**
——日後任何改動都要在斷點兩側各驗一次，否則會長出「只有某個寬度壞掉」這種最難發現的缺陷。
B 或 D 單獨採用則只有一套。接受這個代價的理由是手機閱讀是真實場景。

**那個代價現在沒有執行者，這件事要看得見（PR #115）**：jsdom 沒有 layout，所以
「斷點兩側各自顯示對的那一個形態」**測不到**。`tests/js/row-model-css.test.mjs` 守的只是
**兩種形態都還有宣告**——它會抓到「有人簡化 CSS 時把寬形整段刪掉」（那個刪除不報錯，
只是桌機悄悄變回手機版面），但**不證明渲染正確**。真正補得起來的是 E2E／視覺回歸，
＝ #6 的完整解。**這是 #6 的第 4 個具體用途，而且是第一個由已上線功能產生的。**

**佔位物已定案（2026-09-05）：窄形保留 40px 固定色塊**（有圖放縮圖，無圖放來源色＋來源名縮寫）。
使用者原話：「E 手機版面走固定色塊看起來比較整齊，桌機好像就沒差了」——寬形本來就沒有這一格
（D 形不需要佔位物），所以「桌機沒差」是預期內的。

⚠️ **這裡我先算錯了，值得記下來**：我推導過「方格買不到整齊度」——B 形的列高是**標題折不折行**
決定的（`padding 12 + max(40, rtop 17.3 + gap 3 + 標題 18.2×行數)`），方格只把一行的列從 38.5
墊到 40，**多 1.5px**；而它在 375px 手機上吃掉 49px ＝ 13% 的橫向寬度。比較台也照這個推導加了
「列高範圍」的量測。**但那答的是錯的軸。** 使用者看的是**標題左緣的對齊**：有方格時每一列的
標題都從同一個 x 開始，沒有方格時無圖的列會往左跳 49px，在 31% 那種混合週會變成鋸齒狀左緣。
**我量的是垂直整齊，他看的是水平整齊，而我的指標對後者完全是盲的。**
判準：**「整齊」不是一個軸**，量它之前要先問是哪一個軸。

### ⚠️ 儀器修正紀錄——第一輪的結論是錯的，錯在版面不在模型

**這段留著是因為它是本題最容易重犯的錯誤。** 比較台第一版把四個模型**四欄並排**，
每欄只有約 300px；D 的標題扣掉 76px 寬幅條後只剩約 **150px**。而真實頁面是
`.main { max-width: 860px; padding: 24px 16px }` ＝ **828px**，標題有約 700px。

於是第一輪我看到「D 的標題截斷嚴重」並據此推薦 B——**那個截斷是我的比較版面造成的，
不是列模型的性質**。是使用者當場指出「有可能是因為你四種呈現方式並排造成的，實際頁寬
並沒有那麼窄」。加上寬度切換與**實測截斷率**（單行 ellipsis 與兩行 line-clamp 都算）之後，
他的偏好從 B 翻成 D，最後落在 E。

**判準**：評估一個「佔用某個維度」的設計時，**先確認量測環境在那個維度上與真實情境相符**。
並排比較天生會壓縮每個樣本的寬度，所以它適合比較**垂直節奏**，不適合判斷**水平擁擠**。

### 剩下的那一半：把純函式搬進獨立模組（**未做，需要你決定**）

價值在於**已有能跑的系統可以反推理論**，不在於技術新穎。

### 08-31：儀器錯了——標題 token 表擋不掉這種雜訊

**起因**：原訂 08-31 動手填政策 token 表。填之前先做一件事——**把被標成「離題」的那幾篇的正文讀出來**

| 標題（節錄） | 類別 | 正文長度 |
|---|---|---|
| 駕艙機車「台灣這時間交車」…違規開罰 **36000** 元 - 風傳媒 | 路權政策 | **186 字**（真正文） |

**發現二：被標成「離題」的那兩篇，其中一篇是切題的。** 風傳媒那篇的正文主體是

## 桶分數門檻殺乾淨小桶（門檻是對「未過濾的桶」校準的）

**提出**: 2026-08-08，spec 012 量測 SC-004 時發現（**實測副產物，不是推測**）

（`score = Σquality × log(來源數+1) × log(天數+1)`，**三個因子同時縮小**），於是一個**乾淨但小**
的桶會跌破門檻、整桶不發布——連它的 on-topic 文章一起帶走。

**實測（spec 012，E1）**：`機車事故 · 中央社` 過濾後剩 2 篇乾淨事故文、分數 0.63，
`min_threshold: 1.5` → 不發布。012 的 4 筆 on-topic 損失裡有 **3 筆是這個原因**（另 1 筆才是規則漏抓）。
這正是 SC-004 卡在 L0 上不去 L1 的唯一原因——**不是 token 沒調好**。

**與 spec 010 是同一個結構問題**：010 的 道安政策 singleton 天花板 0.22 vs 門檻 1.0，
也是「內容沒問題，但量體撐不起分數」。010 用 digest（聚合）繞過去，沒有解掉門檻本身。

**已量測否決的兩條捷徑（別再走一次）**：

| 方案 | 實測結果 |
|---|---|
| (a) 全面降 `category_min_threshold` | 掃到 ≤1.0 時離題比例**爆回 100%**——髒桶跟著一起復活 |
| (b) 桶分數改用「過濾前」計算 | 離題 **100%**、SC-001 直接失守——該死的爛桶不再死 |

**核心難點**：同一個門檻同時殺乾淨小桶與髒桶，而**用分數分不開它們**——因為分數不含相關性資訊，

### ⚠️ 解法換過：不是「補來源」（2026-08-10，spec 013／PR #86）

**「補來源」的前提查證後不成立。** 07-20 加的六個政策來源自那時起**產出 179 篇**——

- 其餘來源的標題**帶了 taxonomy token**（`禁行`→路權政策、`行人`→行人事故、`路口`→路口安全）

同一個結構）。兄弟類別的來源**比政策池本身分散一倍**：distinct 8／最大來源 24%，
而政策池是 distinct 4／最大 73%。

## embedding 429 導致靜默跳過去重（09-07 新增）

**提出**: 2026-09-07，查週報 runtime 異常（15m10s，首次撞破憲章 IV 的 10 分上限）時撞到。
runtime 只是徵兆，真正的問題在下面。
**分數**: **6.1**（C1 2／C2 1／C3 3）——**全表最高**。
**觸發點**: **已經在燒**，不需要等任何事件。

**評分理由**（C1 = 2 而非 3 是保守取值）：損害真實且可復現（查 DB 就看得到），

C1 應升到 3、總分 7.8。C2 = 1：它汙染 OQ#2 的儀器，但不擋你動手放寬比對窗。
C3 = 3：第一步只是補一行 warning。

**成因是 Gemini embedding 端點的 429**（`generativelanguage.googleapis.com/v1beta/models/gemini-embedding-2:embedContent`）：

只打 Gemini 這一個端點；而 09-07 那次的 log 每分鐘密度顯示 setup 段與正常週幾乎相同

且與 429 視窗（`01:37:37–01:44:16`，6m39s）重疊。

### 為什麼它是靜默的（這才是要修的東西）

```python
# src/analyzer.py
273:  logger.warning("[embedding] 生成失敗：%s", e)   # 逐筆 WARNING，沒有彙總
274:  return None                                    # 不重試
...
343:  no_embed = [a for a in candidates if a.get("embedding") is None]
389:  result = deduped + no_embed                    # 直接放行，不去重
```

`no_embed` **只在 343 被算出來、389 被使用，中間沒有任何 log**。
而同一個函式 329–331 行的註解自己寫著：

> 「沒有 embedding 鍵」與「生成失敗（值為 None）」**必須分開報**：前者代表呼叫端漏了
> `attach_embeddings`，後者是 API 掛掉。兩者的後果相同（不去重）但成因不同。

**只有前者有 warning（`never_attempted`，334 行），後者沒有。**
這是一條**宣告了但沒有執行者**的規則（`~/.claude/rules/decision-style.md` §三），
而這次真的發生的正是沒有執行者的那一半。

### 連帶影響

- **OQ#2（`embed_dedup` 比對窗）的儀器被汙染**：`scripts/measure_embed_dedup_gap.py`
  只看得到**有向量**的文章。它 09-05 量到「1252 篇有嵌入、1685 對 ≥0.88 仍並存」，
  那份數字取樣時 W37 還沒發生。**在缺口補回來之前重跑它，得到的殘餘重複會偏低**——
  沒有向量的那 71 篇根本不會出現在分母裡。
- **09-07 digest 池**：標記的 52 條連結裡有 **7 篇無向量**。

### 修法（兩段，不要混成一件事）

1. **補彙總 log**（一個 PR，無新依賴）——在 `embed_dedup` 印出 `no_embed` 的筆數，
   比照 334 行 `never_attempted` 的既有寫法。**這一步不解決 429，只是讓損害停止靜默。**
   先做這個，因為在此之前**任何補救都無法驗證有沒有效**。
2. **處理 429 本身**——需要一個決定，不要順手做：重試加退避、降低併發、
   或確認 Gemini 的配額層級（memory `project_gemini_free_tier_risk` 記 2026-06-22
   已轉 pay-as-you-go Tier 1，**那個狀態要重新探測**，不要相信紀錄）。
   ⚠️ 爬升曲線（1 → 11 → 27 → 73）指向配額而非偶發，但**這是 E2 推論不是 E1**。

⚠️ **不要把缺口回填當成第一步**：回填會讓現況數字變好看，卻掩蓋掉「它還在不在發生」。
先讓它發出聲音，再談補救，最後才回填。
